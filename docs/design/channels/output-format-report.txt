Date: 2026-11-14. Measured against goshl v0.0.28.
$W = a scratch working directory

======================================================================
1. VERDICT
======================================================================
The channel format is achievable with ONE combined audio+video ffmpeg job per batch of segments.
Every design choice held up except the frame rate, which needs an owner decision.

| Design choice | Result |
|---|---|
| Fixed-duration segments, forced keyframes, across separate jobs | PROVEN. Split jobs give packet timestamps identical to a single long job, 4 sources x 2 frame rates. |
| Pad to exactly 1280x720 | PROVEN. SPS, PPS, PAT, PMT, SDT byte-identical across 9 sources. Aspect-only gives a different SPS per aspect ratio. |
| CFR through the fps filter | PROVEN, with two conditions: drop "-enc_time_base demux"; phase-align sources whose timestamps sit half a frame off the grid. |
| CFR at 25 or 30 | Works, but wrong rate for this library (section 3). DECISION NEEDED. |
| Muxed A/V in one TS segment | PROVEN with a combined job. The current separate-jobs model does not produce it directly. |
| -map_metadata -1 | PROVEN. Today's VOD output leaks the source title in every SDT; the flag removes it. |
| Real players | hls.js and AVFoundation each played ~110 s through 9-10 item changes, no errors, no stalls. |
| "-fps_mode cfr -r N" instead of the fps filter | DISPROVEN. It discards the -copyts timeline. |

RECOMMENDATION: 24000/1001 with 48-frame segments (2.002 s). The plan still depends only on duration:
boundary i is at i x 2.002 s. All timing results below were reproduced at BOTH 25 fps / 2.000 s and
24000/1001 / 2.002 s, so either choice is supported; nothing else in this report changes with the choice.

Consequence of 24000/1001: a frame is 3753.75 ticks at 90 kHz, so TS timestamps step by 3753 or 3754.
The pattern was identical across jobs.

======================================================================
4. RECOMMENDED EXACT FFMPEG ARGUMENTS (CHANNEL PROFILE)
======================================================================
One job produces segments first..last of one item. It also produces one DISCARDED segment before (overlap,
when first > 0) and one DISCARDED partial segment after (trailing, when last is not the item's last), as
goshl's audio jobs do today.

Notation:
  S     = start of the overlap segment, or of "first" when there is no overlap
  E     = end of "last"
  cuts  = starts of first..last (minus the very first when there is no overlap), plus the trailing start
  G     = floor(S x 48000 / 1024) x 1024   (AAC frame grid, in samples)
  IWxIH = the picture fitted into 1280x720, rounded to even, computed in Go from width, height and SAR
  X, Y  = pad offsets = (1280-IW)/2, (720-IH)/2
  phase = per-item video timestamp phase (only when needed, see 5.3)

ffmpeg -nostats -hide_banner -loglevel warning
  -ss <S - 0.001>   <input args> -i SRC        # video input, same 1 ms lead as today
  -ss <G / 48000>   <input args> -i SRC        # audio input, on the AAC grid as today
  -to <trailing ? min(trailing.End, trailing.Start + 1.0) : E - 0.001>
  -copyts -start_at_zero -muxdelay 0 -output_ts_offset 10.000000
  -map 0:<video index> -map 1:<audio index> -sn -dn
  -map_metadata -1 -map_chapters -1
  -metadata service_provider=goshl -metadata service_name=channel
  -c:v libx264 -preset superfast
  -vf "[setpts=PTS-<phase>/TB,]fps=24000/1001:start_time=<S>[,tpad=stop_mode=clone:stop_duration=<stop - videoEnd + 1.0>],scale=<IW>:<IH>:out_color_matrix=bt709:out_range=tv,pad=1280:720:<X>:<Y>:color=black,setsar=1,format=yuv420p,setparams=color_primaries=bt709:color_trc=bt709:colorspace=bt709:range=tv,sidedata=mode=delete"
  -profile:v high -level:v 3.1 -pix_fmt yuv420p
  -b:v 2500k -maxrate 2500k -bufsize 5000k
  -g 48 -bf 0 -sc_threshold 0 -a53cc 0
  -color_primaries bt709 -color_trc bt709 -colorspace bt709 -color_range tv
  -fps_mode passthrough
  -force_key_frames <S - 0.001>,<each cut - 0.001>
  -c:a aac -ac 2 -ar 48000 -b:a 160k
  -af "aresample=48000,aresample=48000:first_pts=<G>,apad"
  -fflags +bitexact -flags:v +bitexact -flags:a +bitexact
  -f segment -segment_time_delta 0.010000
  -segment_format mpegts -segment_format_options mpegts_flags=+initial_discontinuity
  -segment_list_type csv -segment_list pipe:1
  -segment_start_number <overlap index or first>
  -segment_times <each cut - S>
  <dir>/segment-%05d.ts

HDR sources: replace "scale=<IW>:<IH>:out_color_matrix=bt709:out_range=tv" with the existing tone-map chain
at the fitted size:
  zscale=w=<IW>:h=<IH>:t=linear:npl=100,format=gbrpf32le,zscale=p=bt709,tonemap=tonemap=hable:desat=0,zscale=t=bt709:m=bt709:r=tv
When IWxIH is already 1280x720 the pad step is omitted.
For a 25 fps channel: fps=25, -g 50, 2.000 s segments.

Differences from today's transcode job, and why:

| Argument | Why | Evidence |
|---|---|---|
| Two inputs of the same file | Keeps today's video seek and AAC-grid audio seek unchanged in one process | 5.1 |
| fps=...:start_time=S | Frames land on a grid that does not depend on where the job starts; start_time fills it when the first source frame is late | Django without start_time: first video PTS 10.08 instead of 10.00, and segment 0 swallowed segment 1 (98 frames) |
| No -enc_time_base demux | Matroska's 1/1000 timebase rounds every frame | 5.3 |
| -fps_mode passthrough kept | The encoder must not re-time the filter's output | 5.3 |
| setpts=PTS-<phase>/TB when needed | Sources half a frame off the grid flip between slots | 5.3 |
| Overlap and trailing for the video too | Every kept segment is cut by the same mid-job mechanism, for both streams | 5.1 |
| -sc_threshold 0, -segment_time_delta 0.01 | Only forced keyframes exist; a cut cannot be triggered one frame early | Reasoning only, see risk 6 |
| -bf 0 | Audio starts 0-20 ms after video in every segment | 5.4 |
| -map_metadata -1, -map_chapters -1, -metadata service_*, +bitexact, -a53cc 0, sidedata=mode=delete | Remove title, language, encoder idents, captions, HDR side data | 5.5 |
| pad=1280:720 | Identical SPS/PPS for every item | 5.2 |

-segment_times are relative to the first VIDEO packet. Measuring them from the audio priming packet (21 ms
earlier) shifted every cut by one segment (segment start error 180000 ticks).

from probe data.

5.4 MUXED A/V AND THE JOB MODEL
-------------------------------
The current model does not fit as is: video and audio are separate jobs, pools, caches and files, and the
transcoded-video job has no overlap or trailing segment. A combined job fits with small changes and produced
every table above.

First audio PTS minus first video PTS, over all mid-item segments:

| Setting | Range |
|---|---|
| 25 fps, -bf 0 | 0 to 16 ms |
| 23.976, -bf 0 | 0 to 20 ms |
| 25 fps, -bf 2 | -80 to -64 ms (the cut follows video DTS) |
| first segment of an item | -21.3 ms (priming frame) |

The range exists because 2 s is 93.75 AAC frames. It is deterministic: the segment muxer cuts on the video
keyframe; audio packets with DTS at or after the keyframe's DTS go to the new segment. Segments hold 93 or
94 audio frames.

Alternative that keeps today's jobs: remux a video segment and an audio segment with -c copy. A demux and
remux of one segment reproduced every packet timestamp. It needs three artefacts and three processes per
segment; not recommended.

5.5 METADATA
------------
Today's VOD commands reproduced by hand on Akira, whose container title is
"Dragon Ball Z: La battaglia degli Dei - Extended Edition by danny11" (encoder tag HandBrake 1.7.3).

| Output | Leaks found |
|---|---|

| VOD transcoded audio | Same SDT title. PMT language "eng" from the source. "Lavc63.1.102" ident in the AAC stream |

- For current VOD: adding "-map_metadata -1 -map_chapters -1" in jobTimeline.args() fixes the title leak for
  all three job kinds. It changes segment bytes, so the cache version must move.

  that takes 7.6 s with the fitted size in the first zscale.

SegmentsPerJob defaults to 4, which with overlap and trailing on video means 11 s encoded for 8 s kept.
Channel playback is sequential, so a larger batch cuts the overhead (15 segments: 33 s for 30 s).

======================================================================
7. RISKS AND OPEN POINTS
======================================================================
1. Frame rate choice (section 3). 25 or 30 fps makes most of this library judder.
2. Hardware encoders are untested. Everything here is libx264. Identical SPS/PPS, -bf 0, fixed GOP and
   forced IDR must be re-checked per encoder (VideoToolbox, NVENC, QSV, VAAPI). The byte-identical SPS also
   depends on every node running the same encoder build.
3. 4K tone-mapped sources are close to real time in docker on this machine (about 1.3-1.7x, once below 1x).
   A slow job stalls the live edge, so upcoming segments probably need producing ahead of the clock.
4. Audio joins are not sample-exact for sources with irregular audio timestamps (0.7 ms spread on the
   44.1 kHz file; the chain is today's VOD chain). A larger batch makes it rarer. No filter-level fix found.
5. Timestamp phase. Without the per-item shift, an MKV starting half a frame late loses and repeats about
   29% of frames. Where source and channel rates differ slightly (24.000 vs 23.976) the phase drifts across
   the half-frame point periodically; that case is untested.
6. Scene-cut keyframes near a boundary. With today's 0.05 s delta and frames 40-42 ms apart, a scene-cut
   IDR one frame before a boundary would cut early. Not reproduced; -sc_threshold 0 plus a 0.01 delta
   removes it for channels. May be worth a look for current VOD transcodes.
7. Sources not tested: no audio track (the muxed job needs a generated silent track to keep the format
   identical); audio that ends early or starts late; interlaced video; multiple audio tracks; HLG and
   10-bit PQ (only 8-bit PQ was run); HTTP sources (two inputs mean two connections per job).
8. Players not tested: Safari, iOS/tvOS, ExoPlayer, smart TVs. Their tolerance of size changes is unknown,
   which is the argument for padding.
9. Loudness differs between items and is not normalised; a per-job loudnorm would not be consistent
   across joins.
10. Item ends. Video overruns the plan by up to one frame and the last segment is short (or up to D + 0.5 s
    with mergeTail). frames must take EXTINF from the plan in frames, and EXT-X-TARGETDURATION must cover
    the merged tail.
11. Encoder settings are a first guess. 2.5 Mbit/s capped VBR, superfast and 160 kbit/s audio exercised the
    pipeline; they are not tuned for quality. 5.1 downmix uses ffmpeg's default matrix.
12. Padding burns letterbox bars into the picture and upscales SD.
